# ExcelTask MCP: take the narrow Excel executor to 11

**Scope and evidence date.** This is a strategic brief for `rjgold98/excel-task-mcp` at
[`ff5f3ae`](https://github.com/rjgold98/excel-task-mcp/tree/ff5f3ae657c214d4f992c2300e604170b7a0ed56), researched 2026-08-12. `v0.17.1` is the latest release tag; this inspected `main` commit is one commit ahead and therefore unreleased. Facts below are sourced; statements marked **Inference** are recommendations derived from them. “No counterpart found” means only the surveyed projects did not document one—not that none exists.

## Review request

This is a decision packet for the lead agent and owner, not an implementation PR. It deliberately changes no runtime behavior, product contract, roadmap status, or release notes. Please review the evidence and give each proposal a clear disposition: **accept**, **revise**, **defer**, or **decline**.

Recommended sequence:

1. **Accept now:** keep the two known field defects as the only P0 implementation work—`CopyExhibit` external-link corruption and false-exact `UseOpen` identity.
2. **Accept after P0 as the measurement gate:** build a reproducible benchmark corpus before adopting or advertising speed changes.
3. **Explore after P0:** finish one private mutation transaction shared by generic writes, formula edits, and macro edits without changing the public tool/runtime seams.
4. **Prototype only:** run a non-shipping differential experiment that compares direct-file verification with separate-Excel verification. Under the current contract, OOXML results must not replace reopen verification or determine `Completed`; shipping that change would require an explicit product-contract decision.
5. **Defer unless evidence changes:** persistent Excel sessions, a generic operation framework, broad tool expansion, MCP resources, and durable Tasks.

The specific review questions are:

- Are the two P0 defects framed with the right acceptance gates?
- Should the shared private mutation transaction be the next architectural deepening after those fixes?
- Is a non-shipping direct-file differential experiment worth running while reopen-in-Excel remains the universal completion gate?
- Which MCP compatibility experiments, if any, deserve named-client tests now?

## Executive verdict

ExcelTask already has the right strategic wedge: a single, bounded MCP tool; per-call private COM worker; an explicit workbook-binding contract; `Plan`/`Apply`; reopen verification; and an explicit `Unknown` outcome after an interrupted mutation. **But two unresolved field failures make reliability—not optimization—the P0:** `CopyExhibit` produced 305 unintended external-reference formulas and ended `Unknown`; and `UseOpen` called a target “exactly open” based on a ROT display-name match, then bound a stray `Book1`/add-in artifact. [Roadmap field log](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/ROADMAP.md)

Once those are fixed, its greatest performance win is **coordination reduction**, not faster Excel: its own work-computer comparison reports a smaller tool surface and fewer model/MCP turns, while its Excel execution was 13% slower. The comparison was only one run per workflow, so it is a credible lead, not a benchmark. [Project roadmap](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/ROADMAP.md)

Take it to 11 by preserving that boundary and doing four things in order:

1. Fix both field identity/mutation failures before performance work; exact binding and zero unintended external links are product invariants.
2. Make every speed claim reproducible with a versioned benchmark matrix that separates model orchestration, process startup/death, COM dispatch, calculation, save, reopen, and bytes.
3. Make the current reliability contract more observable: expose safe-boundary phase progress, preserve cancellation semantics, and keep the existing task ID as receipt/trace correlation. After `Unknown`, require a fresh inspect/plan reconciliation; do not imply a durable lookup that the stateless server does not provide.
4. Use OOXML for cheap, read-only planning and as a non-shipping differential verification experiment. Reopen-in-Excel remains the universal completion gate under the current contract; replacing it would require an explicit contract decision. Do not add a headless mutation engine until fidelity requirements are explicit.

### What maintainers and users actually talk about

Across first-party issue trackers, the recurring complaints are operational rather than architectural slogans:

- **“You touched the wrong workbook.”** ExcelTask’s field log reports a false-exact `UseOpen` result; negokaz reports a path/open-workbook mismatch leaving Excel in a damaged UI state. Exact identity must be proved by binding and reading the workbook identity, not inferred from a display name. [ExcelTask field log](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/ROADMAP.md), [negokaz #75](https://github.com/negokaz/excel-mcp-server/issues/75)
- **“Excel or the file stayed stuck.”** Microsoft documents modal dialogs that can block an automation thread indefinitely; negokaz reports a screenshot path retaining a workbook lock for the server session. Ownership, deadlines, lock proof and cleanup evidence are product behavior. [Microsoft KB 257757](https://support.microsoft.com/en-us/help/257757/considerations-for-server-side-automation-of-office), [negokaz #70](https://github.com/negokaz/excel-mcp-server/issues/70)
- **“The formula worked here, not there.”** sbroenne has a current report of COM formula operations failing on de-DE Excel 2019. Locale and Excel-version matrices matter more than a generic formula feature claim. [sbroenne #750](https://github.com/sbroenne/mcp-server-excel/issues/750)
- **“The tool schema itself broke the client.”** negokaz has a current Gemini schema rejection; haris has a current issue about migration from deprecated SSE behavior. Contract compatibility needs schema fixtures against named clients, not only server-side serialization tests. [negokaz #77](https://github.com/negokaz/excel-mcp-server/issues/77), [haris #153](https://github.com/haris-musa/excel-mcp-server/issues/153)
- **“The MCP exposed too much.”** haris’s issue tracker and advisory show how paths, formula policies and unauthenticated network transports become security seams. A local stdio server still needs path confinement; an HTTP server additionally needs authentication and Origin/host controls. [advisory](https://github.com/advisories/GHSA-j98m-w3xp-9f56), [haris #145](https://github.com/haris-musa/excel-mcp-server/issues/145), [haris #149](https://github.com/haris-musa/excel-mcp-server/issues/149)
- **“Too many tools cost model time.”** sbroenne attributes a large MCP-vs-CLI token gap to its schema catalog, while mcp-server-xlwings explicitly consolidated tools for faster client response. Both are first-party, self-reported evidence—not independent benchmarks—but they point in the same direction as ExcelTask’s one-tool design. [sbroenne README](https://github.com/sbroenne/mcp-server-excel), [xlwings changelog](https://github.com/geniuskey/mcp-server-xlwings/blob/main/CHANGELOG.md)

## MCP operating best practices for this server

- Keep one tool and the existing strict operation union. Keep `Plan`/`Apply`, overwrite intent, workbook binding, and bounded output explicit. Preserve the existing `outputSchema` plus `structuredContent`. The 2026-07-28 spec says a structured result should also serialize the JSON in `TextContent` for backwards compatibility; ExcelTask currently returns only a short human summary there. Test the named Copilot client before duplicating the full receipt, budget both copies if needed, and document the compatibility tradeoff if compactness wins. Do not add a confirmation token: the current stateless resubmission contract is deliberate. [MCP tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Keep the one tool conservatively annotated as destructive. MCP annotations describe a tool as a whole and cannot truthfully mark only the read branches of this operation union; they are hints in any case, not authorization. Exact binding, preconditions, and `overwriteConfirmed` remain enforcement. [MCP tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- If the current SDK/client path can carry a progress token end to end, report safe-boundary progress (`preflight`, `inspect`, `plan`, `Excel-started`, `mutate`, `save`, `reopen-verify`, `cleanup`) and honor cancellation between phases. On client cancellation, stop only at a safe boundary and retain only the privacy-filtered operator diagnostics permitted by the current trace policy; MCP normally sends no tool result for the cancelled request, so client reconciliation requires a fresh inspect/plan. Return `Unknown` when a server deadline or worker failure occurs after dispatch while the request is still active. [Progress](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/progress), [Cancellation](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/cancellation)
- Consider private, parameterized resources only for large, immutable inspection artifacts after client compatibility is measured; return a small summary and fingerprint from the tool. Validate resource URIs and keep workbook values out of diagnostic logs. [MCP resources spec](https://modelcontextprotocol.io/specification/2026-07-28/server/resources), [MCP caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)
- Keep stdio clean: stdout is MCP protocol traffic only, diagnostics go to stderr. If Streamable HTTP is ever added, bind/authenticate/validate Origin and implement explicit workbook/STA serialization; it is not a transport-only change. [MCP transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), [HTTP transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
- Do not put model credentials or planning inside the server. MCP Sampling is deprecated in the 2026-07-28 revision and new implementations should not adopt it; ExcelTask’s deterministic executor is the correct side of that seam. [MCP sampling](https://modelcontextprotocol.io/specification/2026-07-28/client/sampling)

## Architecture review: where a deeper module would pay off

The current public boundaries are already good and should remain stable:

```mermaid
flowchart LR
    Client["MCP client"] --> Tool["one excel_task tool"]
    Tool --> Engine["Core task engine"]
    Engine --> Runtime["IWorkbookRuntime"]
    Runtime --> Supervisor["private-worker supervisor"]
    Supervisor --> Worker["bounded worker protocol"]
    Worker --> Excel["one Excel STA adapter"]
    Excel --> Verify["save, close, prove, verify, promote"]
```

This is a deep interface: one request hides normalization, policy, inspection, confirmation, execution, verification, cleanup, and receipt shaping. The strongest opportunities are internal seams that concentrate repeated policy without adding public concepts.

| Candidate | Current pressure | Deeper shape and deletion test | Disposition |
|---|---|---|---|
| **Finish the mutation transaction** | Generic writes use a shared mutation path, but formula and macro edits still maintain parallel save/close/prove/lock/reopen/promote tails. A cleanup, promotion, or `Unknown` rule can drift between them. | Keep operation-specific preflight and verification meaning where they are; concentrate only the private post-mutation transaction. If that module were deleted, all three mutation families—not unrelated reads/audits—should lose their lifecycle implementation. | **Strong; explore after the two P0 correctness fixes.** [generic](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/src/ExcelTask.Excel/ExcelWorkbookRuntime.Mutation.cs), [formula](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/src/ExcelTask.Excel/ExcelWorkbookRuntime.cs), [macro](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/src/ExcelTask.Excel/ExcelWorkbookRuntime.Macro.cs) |
| **Separate supervision policy from worker transport** | `SupervisedWorkbookRuntime` owns deadlines, acceptance, identity evidence, cleanup and status normalization while also launching the process, reading JSON lines and parsing frames. Transport changes therefore touch safety policy. | Concentrate launch/read/frame-validation mechanics behind the existing supervisor while leaving `Unknown`, ownership and cleanup decisions together. Deleting the transport side should break protocol tests without erasing the supervisor’s outcome policy. | **Worth exploring when this area next changes; preserve current semantics first.** [supervisor](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/src/ExcelTask.Excel/SupervisedWorkbookRuntime.cs) |
| **Concentrate request compilation inside the Task Engine** | `ExcelTaskEngine` combines orchestration and receipt policy with the closed-union normalization rules for every operation. Adding an operation touches several switch sites. | A private request-compilation module could own normalization while the engine retains orchestration. The leverage is uncertain because there is one backend and the exhaustive switches currently make the closed union visible. | **Defer until repeated operation churn proves the seam.** Do not build a generic executor registry now. [engine](https://github.com/rjgold98/excel-task-mcp/blob/ff5f3ae657c214d4f992c2300e604170b7a0ed56/src/ExcelTask.Core/ExcelTaskEngine.cs) |

Two recent refactors are positive controls, not new targets: `ReceiptBounds` centralizes one policy across trust boundaries, and the existing generic mutation path already removed repeated lifecycle code. `ExcelSession` should also remain cohesive because workbook identity, COM ownership, and close order are one safety responsibility. Avoid splitting modules merely to reduce line counts.

### Measurements that make “faster” meaningful

For every canonical workflow (structure scan, audit, bounded read, constant write, formula repair, copy exhibit, macro edit), capture:

`request bytes → model input tokens → model turns → MCP calls → worker spawn → Excel launch → COM dispatch count → calculation → save → reopen verify → cleanup → response bytes`.

Report median, p95, failure rate, `Unknown` rate, process/file-lock leak rate, and validation coverage. Split **cold** (fresh Excel/worker) from **warm** runs; do not hide calculation cache effects. Compare only matched client model/prompt, Excel build, workbook hash, hardware and server commit. Microsoft explicitly recommends repeated measurements because subsequent calculations and Windows caching change timing. [Microsoft calculation measurement guidance](https://learn.microsoft.com/en-us/office/vba/excel/concepts/excel-performance/excel-improving-calculation-performance)

## What not to build

- Do not turn this into a broad low-level Excel command catalog, generic dialog clicker, model-hosting service, or unattended web service. It discards the differentiation and conflicts with Microsoft’s Office Automation boundary. [KB 257757](https://support.microsoft.com/en-us/help/257757/considerations-for-server-side-automation-of-office)
- Do not add a long-lived shared Excel process merely to remove startup time. **Inference:** the modest startup saving is not worth weakening process ownership, stale state isolation, exact identity, and recovery.
- Do not promise cancellable COM calls, zero-risk `DisplayAlerts=False`, or universal Open XML fidelity. Report `Unknown`, preserve evidence, and reconcile.
- Do not add arbitrary formula/VBA/general automation acceptance merely for parity. Formula fidelity, locale, macros, queries, add-ins, and dialogs have distinct failure modes; broaden only when a bounded workflow has fixtures and reopen-verification gates.
- Do not quote project or competitor token/latency figures as independent benchmarks. Label them self-reported/descriptive until the proposed harness reproduces them.
